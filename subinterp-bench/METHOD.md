# 测量纪律

这份清单不是风格偏好。**每一条都对应一次量出假结论的经历** —— 有的花了两个小时,
有的差点让人去优化一个不存在的问题,有的让一个真泄漏在分支里躺了七个提交。

改基准之前、重跑基准之前、以及看到一个"惊人的数"之后,先过一遍这个。
案发经过在 [`../RETRO-subinterp.md`](../RETRO-subinterp.md) 第九节。

---

## 一、对照组

### 对照必须是被测分支的**父提交**,不是上游发行版

```
✗ crates.io 0.29.2          差一个上游改动就够
✓ git worktree add /tmp/pyo3-base <父提交 SHA>
```

**这一条造出过 92% 的假回归。** 上游在 `dfdbc46` 之后把 `#[pyclass]` 改成了 GC 跟踪,
拿发行版当对照,量到的是**上游的改动**,记在了自己头上 —— 而且方向和量级都足够逼真。

### 对照组要能真的跑

给探针加东西时留意:一旦对照组因为那个东西**加载不了**,它的整列就废了。
`probe/` 的子模块和 abi3 都在 cargo feature 后面,默认关,原因就是这个。

## 二、计时循环

### 不要留活被测对象

```python
✗ best = min(... [f() for _ in range(400_000)] ...)     # 40 万个活对象
✓ for _ in range(N): f()                                # 用完就扔
```

量到的会是 GC 遍历而不是构造。**在两个 GC 跟踪状态不同的版本之间,单这一条就能凭空
造出 2 倍差距。**

### 计时窗口只包被测部分

子解释器的 setup(创建 + import + 预热)几十到几百毫秒,包进分母而计数只统计
测量循环,会**系统性低估**它。分两段 `exec`,只计时第二段。

### 免 GIL 下,harness 自己不能持有共享对象

```
闭包变量 (LOAD_DEREF,12 线程共用一个 cell)      8.9 M/s   0.44×
模块全局 (LOAD_GLOBAL,有优化路径)            141.3 M/s   6.78×
```

同一个负载,单线程都是 20.6 M/s,**多线程差 16 倍**。12 个线程读同一个闭包 cell,
每次读都 incref —— 正是这套基准要测的那个争用,在计时循环里被复现了一遍。
被测表达式和 worker 函数都要 exec 进**真正的模块全局**。

## 三、判据本身

### 先确认你问的是不是那个问题

```
✗ 「建 16 个,一起关,立刻收回多少」   0% 有歧义 —— 可能只是延迟释放
✓ 「一次只活一个,做 400 次,斜率多少」  不为零就没有第二种解释
```

**这一条上浪费了两个小时**,追一个模棱两可的指标。`reclaim.py` 和 `leak.py` 问的
不是同一件事,**两个都要跑**。

### 一个坏值如果能有第二种无害解释,它就不该用来定案

### 判据也要和自己对账

`stress.py` 曾经一边印"总量在减速"一边判"持续增长" —— 因为斜率按**轮**算而总量按
**解释器**算。**判据也是仪器,仪器也要有对照。**

## 四、重复与噪声

### 单次测量不作数

同一格重复五次能给出 **0.91× 到 0.99×**。拿其中一次当结论,就会为一个不存在的差异
去找解释 —— 那次找了三个,全被证伪,因为根本没有需要解释的东西。

`topology.py` 每格跑 `REPS` 次,印**中位数 ± 跨度**。**跨度大于两列之差时,那个差不是结论。**

### 整齐的数字是可疑的

真实测量给 `−0.4%`,不给 `0.0%`。正好是零通常意味着**某条路径压根没执行**。
那个 2.6 MB/解释器的泄漏,线头就是一个太圆的零。

### 先把账算平,再怀疑代码

```
账面差 42 ns
  而这条路上改动只多做一件事:一次每解释器的类型对象查找
  实测      0.39 ns(父提交)→ 2.22 ns(本分支)   =  +1.83 ns
  其中      PyInterpreterState_Get + GetID 这对 FFI 占 1.5 ns
  ─────────────────────────────
  有出处的只有 1.83 ns,账面上是 42 ns
```

**差 23 倍。钱对不上说明账本有问题,不是花销有问题。**

(这本账自己也错过一次:早先的版本把 FFI 那一对和类型查找**并排相加**,
可 FFI 就在查找里面,加不得。账本要能自己对上,不然它也是个坏仪器。)

## 五、失败与崩溃

### 崩溃是结果,不是错误

对照组建对象会 SIGSEGV / SIGABRT —— **那是这条分支存在的理由**,必须出现在表里。
每格独占一个子进程,被信号打死时把**信号名**打出来。

### 失败要带原始信息,不要哨兵词

```
✗  失败 / invalid / unknown
✓  ImportError: module abi3t does not support loading in subinterpreters
```

`audit_caches.py` 里两个解析不到的目标,打印的是它们抛的 `AttributeError` 原文,
**不猜,也不算进"安全"那一栏**。

## 六、覆盖维度

### 行为维度和构建维度是两个维度

这套基准把行为测得很密,把构建配置测成了**零** —— 全是默认 ABI、全是顶层模块。
于是三个 bug 一个都没抓到,全由第一个真实消费者(polars,用 `abi3-py310` +
`wrap_pymodule!`)免费发现:

```
① 限定 API 下编不过      PyObject_CallMethodNoArgs / OneArg 不在里面
② 限定 API 下 slot 发不出  abi3 的编译期 cfg 取【最低】版本,gate 成了空操作
③ 占位符泄漏到子模块      ②的修法自己造的
```

`build.sh` 现在编 **8 份**:{对照, 本分支} × {默认 ABI, abi3-py310} × {顶层, 含子模块}。

### 二分的答案取决于探针

同一批提交,换个探针再分一次,答案从第五个提交变成了**第一个**。
探针照不到的路径,二分会把责任推给第一个碰到它的提交 —— **那个提交是无辜的。**

### 判据做成脚本全量跑,比逐个想更可靠

"持有 PyObject 吗 → 是永生的吗 → 是堆类型吗"这条判据用了很久,一直是手工套用。
做成 `audit_caches.py` 全量跑一遍,当场翻出 **11 处从没被检查过的**。

### 测试的形状决定了它能看见什么

压测跑了 4000 个解释器报"收敛",而同一时刻分支里有个线性不收敛的泄漏 —— 因为它的
解释器体恰好是唯一安全的那种写法。

写压测时想的是"怎么把这套机制**用起来**",而 bug 藏在"怎么把它**用坏**"里。

**修完 bug 之后要问:它为什么躲过了我已有的测试?那个答案通常比 bug 本身值钱。**

## 七、定位

### 假设可以无限生成,埋点只要一行

四个假设全错之后,继续想第五个是负收益。

### 埋点打在状态转换的**两侧**

```
只打「后」   得到一个数字 3    → 继续猜谁持有那三个引用(查不完)
打两侧      得到一个事实 3→3  → "为什么放手没生效"(能在源码里查到)
```

### 把假设做成开关,而不是做成争论

"gc 遍数够不够"可以争一小时,也可以做成环境变量扫 `0 / 1 / 3 / 10`。
后者三分钟,给出的是数据不是意见。

### harness 自相矛盾时,先修 harness

```
不 import 扩展   存活 +57.9MB
只 import        存活 +39.4MB   ← 什么都不加载反而更占内存?
```

**被测物可以反直觉,harness 不能自相矛盾。** 修好之前所有结论都不作数 ——
那批数据全部作废重测了。
